# @trycandid/react-native - Development Guidelines

This file gives AI coding agents the repo-specific context needed to work safely in this React Native wrapper for the Candid iOS SDK.

## Project Overview

`@trycandid/react-native` wraps the [Candid iOS SDK](https://github.com/TryCandid/candid-ios-sdk) (in-app user testing and voice feedback flows) for React Native. It is built with the Expo Modules API and works in both Expo and bare React Native apps.

- One npm package with one native module: `CandidReactNative`.
- The native SDK is consumed as a binary XCFramework, downloaded checksum-pinned at `pod install` time. The SDK source is not in this repo; the private source repo lives at `../candid-ios-sdk` on Candid machines.
- Android and web are intentional no-ops: every JS call must remain safe to make from shared code.

## Repository Shape

- `src/`: public TypeScript API (`index.ts`), native module declaration, and types mirroring `Candid.Configuration`.
- `ios/`: the Expo module (`CandidReactNativeModule.swift`) and `CandidReactNative.podspec`.
- `ios/Frameworks/`: the downloaded `CandidSDK.xcframework` (git-ignored, created by `pod install`).
- `android/`: no-op stub module so cross-platform JS is safe.
- `plugin/` + `app.plugin.js`: Expo config plugin (deployment target at least 15.1, `NSMicrophoneUsageDescription`). The podspec separately mirrors the host app's `expo-modules-core` iOS floor when it is higher (e.g. 16.4 on Expo SDK 57) so CocoaPods can resolve the `ExpoModulesCore` dependency across Expo SDK versions.
- `example/`: prebuilt Expo app mirroring the iOS SDK's `Examples/CandidSample`.
- `build/`: compiled module output (generated by `npm run build`, do not edit).

## Key Implementation Notes

### Overlay hosting and touch passthrough

`CandidOverlayPresenter` in `ios/CandidReactNativeModule.swift` attaches the overlay to the app's root view controller through `Candid.attachUIKitOverlay(to:)` (SDK 0.2.0+). The SDK hosts the overlay in a passthrough container that only intercepts touches landing on visible Candid UI; everything else falls through to React Native.

Two constraints shape this design; keep both when touching it:

- The overlay must live in the app's main window: the SDK's ReplayKit capture records that window only, so a separate overlay `UIWindow` is invisible in recordings.
- Touches outside visible Candid UI must reach React Native, including while the recording bubble is on screen (users interact with the app during recording). Do not attach a plain `UIHostingController` view over the React Native root view: `_UIHostingView` hit-tests its entire bounds even when its SwiftUI content disables hit testing, which freezes taps and scrolling in the host app.

### Main-actor bridging

The Candid public API is main-actor isolated; Expo module functions run on the JS thread. All `Candid` calls go through the `onMain` helper (ordered `DispatchQueue.main.async`, not unstructured `Task`s). Keep new bridged calls fire-and-forget or handle return values explicitly.

### Binary SDK delivery

`ios/CandidReactNative.podspec` pins `candid_sdk_version` and `candid_sdk_checksum`, downloads `CandidSDK.xcframework.zip` from the public GitHub release during `pod install`, and verifies the SHA-256. Bumping the SDK version means updating both values. Do not vendor the XCFramework into the repo or npm package.

### Example app environment switcher

The SDK always targets the production Candid API (`baseURL` is internal to the SDK by design). The example's Local / Staging / Prod switcher works through a debug-only `URLProtocol` in `example/ios/candidreactnativeexample/AppDelegate.swift` that rewrites Candid API requests to the base URL the JS side persists via React Native's `Settings` API (key `candidBaseURLOverride`). This is the React Native counterpart of the iOS sample's `@testable` base URL override. Keep it example-only and `#if DEBUG`; do not expose a base URL in the wrapper's public API.

## Public API Stability

Keep the JS API compact and mirrored on the SDK's public API: `configure`, `registerTrigger`, `log`, `reset`, `addCandidEventListener`. Adding optional configuration fields (with matching `Record` fields in Swift) is safe; renaming or removing exported symbols, or changing call signatures, requires explicit approval. Types in `src/CandidReactNative.types.ts` must stay in sync with the Swift `Record` structs in `ios/CandidReactNativeModule.swift`.

## Common Commands

Run from the package root:

```bash
npm run build        # type-check and build the module to build/
npm run lint
```

Example app (run from `example/`, never `expo run:ios` from the package root — it would try to reinitialize the module's ios/ folder):

```bash
cd example
npm install
npx pod-install ios
npx expo run:ios             # simulator
npx expo run:ios --device    # physical device
```

CI-style native build of the example:

```bash
xcodebuild -workspace example/ios/candidreactnativeexample.xcworkspace \
  -scheme candidreactnativeexample -configuration Debug \
  -destination 'generic/platform=iOS Simulator' build
```

`pod install` may need `LANG=en_US.UTF-8 LC_ALL=en_US.UTF-8` on some machines.

## Testing Expectations

There is no unit test suite yet. For any change to the native module, overlay hosting, or the example app: build the example, run it on a simulator, capture a screenshot, and inspect it before considering the work done. Touch passthrough regressions are the highest-risk failure mode; verify that taps and scrolling work in the example whenever the overlay hosting changes.

## Guardrails

- **Commit messages:** Write messages as a human contributor would. Never mention Cursor, Codex, or Claude Code in the subject, body, or trailers. Do not add `Co-authored-by` lines for AI tools.
- Keep diffs scoped to the requested change.
- The example app's iOS project is pre-configured (microphone permission); the config plugin is intentionally not listed in `example/app.json`.
- Do not commit `ios/Frameworks/`, `build/`, `node_modules/`, or Xcode user state.
- Do not add dependencies unless they remove meaningful complexity.
- When changing the public JS API, integration behavior, or user-visible behavior, update `CHANGELOG.md` and `README.md`.
- Do not commit secrets or API keys; the example persists API keys in `UserDefaults` at runtime only.
